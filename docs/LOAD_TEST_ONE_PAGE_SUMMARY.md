# 말모아 백엔드 PostgreSQL 부하 테스트 요약

> 실행일: 2026-10-29
>
> 목적: 실제 PostgreSQL을 사용했을 때 기기 텔레메트리 API가 감당 가능한 부하 구간 확인

## 실제로 구성한 환경

- Spring Boot 서버와 Node.js 부하 발생기를 **서로 다른 프로세스**로 실행
- H2 대신 WSL의 **PostgreSQL 16.15** 사용, Flyway V1~V7 적용 확인
- 테스트 전용 AAC 사용자·기기·Bearer Token 1,000개 생성
- 기기마다 별도 Token을 사용해 실제 인증 및 DB 조회·저장 경로 호출
- Prometheus Metric으로 CPU, JVM Heap, Hikari DB 연결 수 수집
- SQL 상세 로그를 끄고 각 단계 전에 서버를 재시작해 이전 요청의 영향을 제거

## 요청 시나리오

| 기능 | 주기 |
|---|---:|
| Heartbeat | 60초 |
| 위치 전송 | 10초 |
| 심박수 전송 | 5초 |

요청 시작 시점은 기기별로 분산했다. 각 단계는 60초 동안 실행했으며, 임시 통과 기준은 오류율 1% 미만, P95 500ms 미만으로 두었다.

1,000개 기기 단계에서는 410건이 10초 안에 응답하지 못해 Timeout 처리됐다. Hikari Connection Pool도 최대치 10개를 사용했고, 750개에서 1,000개로 증가할 때 지연시간이 급격히 상승했다. 따라서 현재 설정으로 실제 사용자 1,000명을 안정적으로 처리한다고 말할 수 없다.

## 결론

이번 PC·시나리오·1분 실행 기준으로 **750개 가상 기기까지는 오류 없이 통과**했고, **1,000개 기기는 통과하지 못했다.** 1,000개 단계가 이미 1분 안에 실패했으므로 실패 요청을 10분 동안 더 누적하지 않고 종료했다.

다음 개선 대상은 기기 인증 때마다 수행되는 DB 조회·Heartbeat 갱신, 트랜잭션 범위, Hikari Pool 크기와 PostgreSQL 쿼리·인덱스다. 개선 후 1,000개 1분 재시험을 먼저 통과시키고 10분 지속 시험으로 넘어간다.

## 결과 해석의 한계

- 서버와 부하 발생기는 별도 프로세스지만 **같은 물리 PC**에서 실행했다.
- localhost 통신이라 실제 Network, TLS, Reverse Proxy 지연이 없다.
- 실제 사람 1,000명이 아니라 주기 요청을 보내는 1,000개 가상 기기다.
- Heartbeat·위치·심박수만 포함했고 SSE, 카드 사용, STT, 리포트, AI 호출은 제외했다.
- 1분 단계 시험이므로 장시간 Memory 안정성은 아직 검증하지 않았다.

원본 JSON과 단계별 Markdown 결과는 Git에서 제외되는 `target/load-test-results/postgres`에 저장된다.
